# 积分商城客服接入说明

日期：2026-10-24。

本期完成 AI 服务及 Ecommerce 后端的积分查询能力：积分 Agent、`points-service` 领域配置、四个只读工具，以及对应数据库和业务接口。原六工具已在2026-10-24合并，旧 HTTP 接口保留兼容；旧测试与原始接口说明保留为历史记录。福利、餐补、员工激励、会员卡券、积分补发及直接创建工单均不在本期范围。

当前积分专家只注册以下四个工具：

| 工具 | HTTP接口 | 职责 |
| --- | --- | --- |
| `get_points_account` | `GET /points/account` | 余额、冻结、到期概况，按需分页查询批次 |
| `get_points_transactions` | `GET /points/transactions` | 发放、消费、返还、过期、冻结流水 |
| `check_points_eligibility` | `GET /points/eligibility` | 商品及数量的兑换资格预校验 |
| `get_order_points` | `GET /orders/{order_id}/points` | 订单实扣、冻结、应返还、已返还及返还状态 |

`get_points_account` 默认 `include_expiry=false`，批次 `expiry_batches` 和批次总数 `total` 为 `null`，表示没有请求批次；不能解读成没有到期积分。需要到期日期或批次时传 `include_expiry=true`，使用 `page`、`page_size` 分页，空页为 `[]`，同时返回真实批次总数。账户概况的证据对象为 `account_id`，具体批次仍为 `batch_id`。

`get_order_points` 同时返回 `deducted_points`、`frozen_points`、`expected_points`、`returned_points`、`status`、`as_of`、`updated_at`。订单取消只可能登记待返还，不能据此声称已到账。两个合并接口均复用后端身份校验，不接收模型提供的用户身份。

### 当前本地积分商城数据

按用户确认，旧演示订单已迁移为积分订单：ORDER_001 为5000积分，ORDER_002 为2500积分，ORDER_003 为3000积分，ORDER_004 为8000积分；ORDER_POINTS_DEMO_001 保持真实已扣2000积分。数值来自演示积分定价或历史扣分，不是现金金额换单位。

订单返回 `payment_type=points`、`total_points`，商品行返回历史 `unit_points`；现金 `total_amount`、`unit_price` 返回 `null`。原现金字段保留在数据库供历史核对，后续商品价格变化不会改写订单快照。只迁移已核验的演示编号，其他非演示现金订单不会被自动改写。商品已配置积分价时不再对用户返回现金报价。

显式迁移入口为 Ecommerce 目录下 `python -m ecommerce_service.points_migration`，可重复执行。旧四单补演示历史初始化发放及等额消费流水，净额为0，不修改积分批次：user_001仍可用4000、冻结200，user_002仍可用1500。迁移同事务更新目标订单已有幂等响应的积分展示字段，保留原操作结果、地址和状态。迁移前本地数据库备份：`backups/ecommerce-before-points-migration-20261024-183831.dump`，同名 `.sha256` 保存摘要，已验证恢复目录可读。

**同级 Ecommerce 后端已实现本文约定的积分接口，并通过本机 Docker PostgreSQL 的真实 HTTP 联调。** 积分账本保存在 Ecommerce，AI 服务只查询和记录证据。演示余额由显式初始化命令创建，不会在查询时伪造。真实企业积分仍需由实际结算系统维护，演示规则不代表企业制度。

## 1. 运行架构

```text
主控 Agent
  ├── 商品 Agent：商品信息、现金价格、积分价格及积分预算筛选
  ├── 订单 Agent：订单信息
  ├── 物流 Agent：配送进度
  ├── 售后 Agent：售后处理进度
  ├── 政策 Agent：平台政策及当前商城积分规则
  └── 积分 Agent：余额、流水、到期、兑换预校验、扣分和积分返还
```

工厂从注册表创建专家，本次只增加领域配置，没有新增另一套调度框架。模型及业务请求均异步执行，身份、执行预算、工具记录与证据校验复用现有 Harness。

## 3. 通用接口约定

- 基础地址沿用 `ECOMMERCE_BASE_URL`，默认 `http://127.0.0.1:8001/api/v1`。
- 所有新增接口使用 GET，不修改积分、订单或有效期。
- 请求携带当前用户 `Authorization: Bearer ...`。用户、企业及商城项目由业务后端根据令牌确定，模型不提供这些身份字段。
- 若用户没有明确指定账户，由后端选择其唯一或默认账户；无法确定时返回明确的业务失败信息，不随机选账户。
- 账户、流水与批次编号作为不透明标识使用。订单和商品编号继续沿用项目的大写、下划线格式。
- 积分数量为 JSON 整数，不能使用字符串、浮点数或布尔值代替；余额和汇总非负，流水变动可为负数。
- 时间采用包含时区的 ISO 8601 字符串。流水日期筛选按 `Asia/Shanghai` 业务日期，起止日期均包含当天。
- 每个查询和订单查询都必须在后端校验当前用户的数据归属。
- 商品列表、商品详情和积分规则也支持可选 `account_id`，AI 工具会透传用户明确选择的账户。价格和规则按该账户的 `project_id` 隔离，不能混用默认项目。

成功响应统一为：

```json
{
  "success": true,
  "code": "OK",
  "message": "查询成功",
  "data": {}
}
```

业务失败可以使用：

```json
{
  "success": false,
  "code": "POINTS_ACCOUNT_REQUIRED",
  "message": "存在多个积分账户，请先选择账户",
  "data": null
}
```

`data` 的具体类型见下表。HTTP 失败和返回字段不符合约定时，不会转成零积分或兑换成功。

## 4. 六个只读积分接口

| 工具 | GET 路径 | 查询条件 | data 类型与必填字段 |
| --- | --- | --- | --- |
| `get_points_balance` | `/points/balance` | 可选 `account_id` | 对象：`account_id`、`available_points`、`frozen_points`、`expiring_points`、`as_of` |
| `get_points_transactions` | `/points/transactions` | 可选账户、事件、起止日期；`page` 默认1，`page_size` 默认20、最大100 | 对象：`account_id`、`items`、`page`、`page_size`、`total` |
| `get_points_expiry` | `/points/expiry` | 可选账户；分页参数同上 | 数组，每项：`batch_id`、`account_id`、`points`、`expires_at` |
| `check_points_eligibility` | `/points/eligibility` | `product_id`；`quantity` 默认1、范围1～99；可选账户 | 对象：账户、商品、数量、`eligible`、`reason_code`、`reason_message`、`required_points`、`available_points`、`checked_at` |
| `get_points_deduction_detail` | `/orders/{order_id}/points-deduction` | 订单在路径中；客户端同时记录并传递 `order_id` | 对象：`order_id`、`account_id`、`deducted_points`、`frozen_points`、`returned_points`、`as_of` |
| `get_points_refund_status` | `/orders/{order_id}/points-refund` | 同上 | 对象：`order_id`、`account_id`、`status`、`expected_points`、`returned_points`、`updated_at` |

### 4.1 流水

`items` 中每一项包含：

```json
{
  "transaction_id": "TXN_EXAMPLE",
  "account_id": "ACCOUNT_EXAMPLE",
  "event_type": "consume",
  "change_points": -500,
  "occurred_at": "2026-10-24T10:00:00+08:00",
  "order_id": "ORDER_EXAMPLE"
}
```

此处仅为字段示例，不是用户真实数据。`order_id` 可为空。

`event_type` 支持 `grant`、`consume`、`refund`、`expire`、`freeze`、`unfreeze`。日期参数名为 `date_from`、`date_to`，格式 `YYYY-MM-DD`。后台需要返回对应筛选条件下的总数，AI 层会复核所引用流水的账户、分页、事件及业务日期。

### 4.2 兑换预校验

后端负责检查余额、账户适用范围、限兑条件、库存等，AI 不通过比较两个数字自行判定可兑换。

`eligible` 必须为布尔值。未满足条件仍是一次成功的查询，即外层 `success=true`、内层 `eligible=false`，并提供可解释的 `reason_code` 和 `reason_message`。

预校验通过不会生成订单或扣分；实际页面提交时，业务后端必须重新检查条件。

### 4.3 扣分和返还

`status` 取值：

| 状态 | 展示含义 |
| --- | --- |
| `not_required` | 无需返还 |
| `pending` | 待返还 |
| `processing` | 返还处理中 |
| `completed` | 返还已完成 |
| `failed` | 返还失败 |

订单取消、售后通过和积分到账是不同状态。`completed` 时实际返还数量不得小于应返还数量。

取消含积分记录的订单时，后端在同一事务登记应返还数量和待返还状态，不增加积分余额。实际返还完成需要结算系统更新批次、流水和订单积分记录；本次没有新增自动退款执行器或积分补发接口。

首版扣分和返还对象按“一个订单对应一个积分账户”约定。若实际业务支持一笔订单从多个积分账户扣分，应先扩展为分账户明细及对应证据模型，不得随意返回其中一个账户冒充全单汇总。

### 4.4 到期批次

后端按到期时间排序，分页返回未过期且有剩余积分的批次。AI 展示后端返回的精确时间和时区，不计算或延长有效期。空页只代表本页没有批次，不代表积分永久有效。

## 5. 商品积分价格和筛选

沿用 `/products` 与 `/products/{product_id}`：

- 新增可选 `points_price`：单件商品所需积分。
- 保留可选现金 `price`：纯积分商品可以没有现金价格，不伪造为零元。
- 新增可选 `allowed_account_types`：账户类型范围信息，由业务后端提供。
- 商品搜索增加可选 `max_points`，表示单件商品积分预算，不代表多件商品总预算。

AI 服务会复核已返回的积分价格。若后端未提供积分价格，按预算筛选会明确失败，不把现金价格换算成积分，也不把赠送积分当作兑换价格。符合预算不等于满足兑换资格，还需要积分专家预校验。

## 6. 积分规则

政策 Agent 复用 `search_knowledge`，指定 `topic="points"` 后发送：

```text
GET /points/rules?query=用户问题
```

`data` 为规则数组，每项包含：

| 字段 | 含义 |
| --- | --- |
| `knowledge_id` | 稳定规则编号 |
| `title` | 规则标题 |
| `content` | 可以引用的规则正文 |
| `source` | 规则来源 |
| `version` | 版本 |
| `effective_at` | 生效时间，包含时区 |

后端只返回当前用户所属商城及项目的当前有效版本。AI 不通过网页资料推定某企业的兑换比例、转赠权限、有效期或退款后延期规则；查不到时说明无法确认。

原 `topic="platform"` 仍沿用原项目的固定平台知识数据，不能把它当成真实企业积分规则库。

## 7. 证据与回复

积分专家引用工具响应中的 `evidence_id`，并使用以下 `resource_id`：

| 查询 | resource_id |
| --- | --- |
| 余额 | `account_id` |
| 流水 | `transaction_id` |
| 到期 | `batch_id` |
| 预校验 | `product_id` |
| 扣分、返还 | `order_id` |

服务端校验真实证据及查询对象后，按命名字段生成积分正文，模型自由文本不参与积分数值、返还状态及有效期的最终展示。主控继续统一对外，跨领域查询按已验证片段组合结果。

积分异常沿用现有转人工机制；没有新增积分调整或工单写接口。
